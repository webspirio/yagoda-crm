# Ягода CRM — інструкції для агента

Демо-CRM прийомки ягоди: React 19 + Vite, стан у zustand з `persist`, жодного сервера й
жодної бази. Публікується як GitHub Pages під базовим шляхом `/yagoda-crm/`.
Грошовий рушій — `src/lib/calc.ts` (округлення до копійки, FIFO-розподіл виплат,
«Разом» візиту). Мова інтерфейсу, коментарів і цього файлу — українська.

`docs/` і `input/` у `.gitignore` свідомо: там прізвища з неанонімізованого файлу клієнта,
а репозиторій публічний. Не розширювати цей ігнор.

## Як запускати перевірки

**Гейт наприкінці ходу — це ТІЛЬКИ швидкий рівень.** У ньому немає `build`, `smoke` і
`coverage`, отже хід може завершитися зеленим, жодного разу не зібравши застосунок. Це
свідомий компроміс на користь швидкості: `tsc -b` у швидкому рівні є, тому непокритим
залишається саме те, що ламається лише у збірці vite (base path, ассети, CSS).

```bash
npm run verify        # швидкий рівень — те саме, що гейт наприкінці ходу (~6 с)
npm run verify:full   # + build, smoke у Chromium, coverage
npm run verify:ci     # форма CI: пропуск теж вважається падінням
```

Кожна перевірка — окрема команда, яку можна запустити сама (`npm run lint`,
`npm run typecheck`, `npm test`, `npm run deadcode`, …). Нічого не існує лише всередині
оркестратора і нічого — лише всередині CI.

П'ять станів, які ніколи не зливаються в один:

| стан | значення | блокує |
| --- | --- | --- |
| `PASSED` | запустилося, минуло | ні |
| `FAILED` | запустилося, впало | так |
| `SKIPPED` | передумови немає — не було де запускатися | ні, але це треба сказати вголос |
| `NOT_RUN` | залежність не пройшла, тому й не пробували | так |
| `UNRUNNABLE` | команда не змогла стартувати (127 / spawn error) | так |

`UNRUNNABLE` — не педантизм. Написати «lint FAILED», коли лінтера просто немає в `PATH`,
означає стверджувати про код те, чого ніхто не перевіряв.

| `smoke` | full (потребує: playwright-browser) (після: build) | Зібраний артефакт, поданий під своїм продакшн-базовим шляхом, піднявся у Chromium без page error і без console error; один візит пройшов від ваги до «Разом» із перевіркою самої суми (не лише підпису) і без «NaN» у тексті сторінки. Далі РІВНО ТРИНАДЦЯТЬ відкриттів розділу, кожне без page error, без console error і без «NaN»: приймальникові «Каса за день», «Ціни дня», «Постачальники», «Залишки», «Ящики» і «Каса точки», а після кнопки ролі «Власник» — «Зведення по сезону», «Собівартість дня», «Переважування», «Середня ціна по мережі», «Аркуш керівника», «Перекази» і ще раз «Постачальники». Різних розділів ДВАНАДЦЯТЬ: «Постачальники» відкриваються двічі навмисно, бо під власником SuppliersPage малює ІНШИЙ компонент (OwnerTable) — інакше цей вигляд не рендерив би жоден тест. Пʼять керівницьких приходять окремими чанками через React.lazy, «Перекази» шостим («Постачальники» — ні, вони в головному, як і нові «Ящики» та «Каса точки»), і в усіх семи під роллю власника чекається саме ВЛАСНИЙ заголовок розділу, а «NaN» перевіряється вже після нього — тому зелене означає відкритий екран, а не Suspense-каркас. ### Свідомі рішення, які легко «полагодити» назад

- **jsdom і @testing-library НЕ встановлені, і це навмисно.** Другий тестовий стек із
  нулем тестів у ньому був би мертвою залежністю, яку `deadcode` справедливо б і показав.
  Якщо колись знадобляться компонентні тести — ставити стек разом із першим справжнім
  тестом, не раніше.
  **Але не читати це як «компонентний рівень покрито».** Playwright відкриває сторінки у
  справжньому браузері й перевіряє, що вони рендеряться без помилок і без NaN — це не
  покриття рядків і не перевірка жодної суми. Покриття `.tsx` зміряне й дорівнює **0,00 %
  (0 з 1 819 рядків у 41 файлі)** — зміряно `npm run coverage` 27.08.2026; e2e-прогін нічим
  не інструментований. Число росте разом із кодом і лишається нулем: 24.08.2026 було
  1 224 рядки у 24 файлах, 25.08.2026 — 1 617 у 39.
- **`shadcn` живе у `devDependencies`, не в `dependencies`.** Це CLI для скафолдингу, який
  застосунок ніде не імпортує (`components.json` посилається лише на його схему). Спочатку
  він лежав у runtime-залежностях і тягнув за собою 2 з 3 адвайзорі; після переносу вони
  стали dev-only, тобто до бандла не доходять. Не повертати назад.
- **Бюджет розміру бандла: стелю піднято НАПЕРЕД 27.08.2026, і це треба читати як
  послаблення.** Запас у `scripts/verify/baselines/bundle-budget.json` тепер
  **25 839 байтів gzip і 93 324 raw** замість 5 003 і 7 415 — приблизно ціла фаза роботи
  (кожна з фаз 2, 3 і 5-6 давала 13–23 KiB gzip). Причина записана в `note` того файлу:
  рішення власника, щоб перевірка «поки не заважала». Три попередні підняття були іншого
  роду — вони знімалися ПІСЛЯ завершеної фази й лише округлювали зміряне; це зроблено
  наперед, у момент, коли перевірка була **зелена** (342 801 зі стелі 348 160). Отже воно
  не розвʼязало жодної проблеми, а відсунуло момент, коли доведеться.

  Що з цього випливає для читача: наступна регресія має шанс проїхати мовчки. Ловити її
  тепер треба очима у виводі `bundle` — він друкує запас на кожному зеленому прогоні, — а
  не чекати червоного. І **рядок «НАСТУПНЕ ПІДНЯТТЯ ЗАБОРОНЕНО, поки не почищено спільний
  шар» скасовано власником, а сам борг не сплачено**: `bits` 38 693 gzip і css 16 925,

  Нульового запасу тут не було б у жодному разі: у першій версії стеля пінилася байт у
  байт і впала на наступному ж коміті через **18 байтів** gzip. Перевірка, яка вимагає
  правки бюджету через 18 байтів, вчить піднімати бюджет не читаючи — тому стеля
  округлюється вгору кроком 5 KiB (gzip) і 20 KiB (raw), а падати мусить РЕГРЕСІЯ: нова
  бібліотека, випадковий імпорт усього пакета.

  **І головне, чого бюджет не ловить у принципі.** Він міряє СУМУ `dist/assets`, а не те,
  що людина завантажує. Зміряно 27.08.2026: 14 файлів, **334,8 KiB gzip** разом, але

  менше половини того, що реально переїжджає до нього мережею. Тому наступним кроком тут
  має бути не чергове підняття, а зміна самої мірки: **стерегти перший чанк, а не суму**.
  Сума росте й тоді, коли приймальникові стає легше — розділення чанків у фазі 3 зменшило

### CI: лампочка чи гейт

`verify.yml` існує і проходить (перший зелений прогін на раннері GitHub — 13/13, 1 хв 16 с).
Але **CI стає гейтом лише тоді, коли для `main` увімкнено required status check**. Це
налаштування репозиторію, не код, тож із самого коду його не видно і жодна перевірка тут
його не забезпечує.

Станом на 2026-08-23 воно **НЕ ввімкнене**: `branches/main/protection` віддає 404,
`rulesets` — `[]`. Тобто зараз червоний `verify` нікого не спиняє від мерджу в `main`.
Єдине, що вже тримається механічно, — `deploy` має `needs: verify`, тому червоне дерево
не поїде на Pages (сайт просто лишиться на попередній збірці).

Увімкнути (потрібні адмінські права на репозиторій; `gh` на цій машині авторизований як
`swefd`, який є адміном в організації `webspirio`):

```bash
gh api -X PUT repos/webspirio/yagoda-crm/branches/main/protection \
  -F 'required_status_checks[strict]=true' \
  -F 'required_status_checks[contexts][]=verify' \
  -F 'enforce_admins=false' \
  -F 'required_pull_request_reviews=' -F 'restrictions='
```

Перевірити, що подіяло:

```bash
gh api repos/webspirio/yagoda-crm/branches/main/protection \
  --jq '.required_status_checks | {strict, contexts}'
```

Що варто знати перед тим, як вмикати:

- `contexts` мусить містити саме `verify` — так називається job у `verify.yml`. Якщо job
  колись перейменують, захист почне вимагати перевірку, якої більше немає, і мерджі
  застрягнуть назавжди.
- `strict=true` означає, що гілку треба оновити від `main` перед мерджем. Це саме те, що
  закриває дірку «обидві гілки зелені окремо, а разом ламаються».
- `enforce_admins=false` лишає адміну можливість пропхати правку в обхід — свідомо, щоб
  зламаний `verify` не заблокував і той мердж, який його лагодить. Якщо потрібна
  безумовна дисципліна — поставити `true`.
- Вмикати **після** того, як `verify` хоч раз пройшов на реальному прогоні. Вимагати
  перевірку, яка ще ніколи не була зеленою, означає заблокувати всі мерджі, включно з
  виправленням.
- Захист гілки також забороняє прямий `git push` у `main` — працювати доведеться через PR.

## Три правила

### 1. Докази під заявою

**Цю таблицю не перевіряє ніщо.** Гейт наприкінці ходу завжди запускає лише швидкий
рівень; він не дивиться, що саме змінилося, і не вимагає відповідних доказів. Тобто нижче
— зобовʼязання, а не механізм. Механічно тримаються тільки п'ять станів, храповики
baseline, заборона ключів приглушення в `knip.json`, храповик винятків oxlint і пороги
покриття в CI.

Не «зроблено», а «зроблено, перевірено тим-і-тим». Відповідність така:

| що змінилося | які докази обов'язкові |
| --- | --- |
| будь-що в `src/` | `npm run verify` (швидкий рівень) |
| `src/lib/calc.ts`, `store.ts`, `seed.ts` | `npm run verify` + `npm run coverage`, і назвати цифру |
| будь-який `.tsx` | `npm run verify:full` — бо саме smoke, а не unit-тести, торкається компонентів |
| `vite.config.ts`, `index.html`, `public/` | `npm run verify:full` (base path ламається лише в збірці) |
| `package.json`, лок-файл | `npm run verify:full` + `npm run deadcode` |
| будь-що в `scripts/verify/`, `.claude/hooks/` | `npm run verify` — цей код теж під `tsc -b` |
| registry перевірок | `node scripts/verify/checks/memo-drift.mjs --write`, інакше `memo` впаде |
| `.oxlintrc.json` overrides | `npm run lint:exempt` — і оновити `baselines/lint-exempt.json` |
| `.gitignore`, будь-що біля `docs/` та `input/` | `npm run pii` — межа публічного репозиторію |
| `package.json`, лок-файл, нова залежність | `npm run verify:full` — там `audit` і `bundle` |
| будь-що, що впливає на розмір бандла | `npm run verify:full` — там `bundle`; запас 25 839 байтів gzip — піднято наперед 27.08.2026, тому регресія може проїхати мовчки: дивитися на число запасу у виводі |

Заявляти успіх без прочитаного виводу не можна. Якщо перевірка не запускалася — так і
казати, а не «мабуть, зелено».

### 2. Пропуски проговорюються вголос

«Швидкий рівень зелений; build і smoke пропущено — немає браузера» — і ніколи
«все зелено». Пропуск означає, що про цю частину не перевірено нічого; це інформація, а
не дрібниця, яку можна округлити до успіху.

### 3. Храповики крутяться лише в один бік

Усі baseline у `scripts/verify/baselines/` можуть тільки зменшуватися. Правило
двостороннє: нова знахідка падає, і знахідка, якої вже немає, теж падає — запис треба
прибрати. Причина в кожному записі обов'язкова, і чекер сам відкидає заглушки
(`TODO`, порожній рядок, коротше за 30 символів).

**Позеленіти, розширивши виняток, — це не позеленіти.** Це найзручніша з доступних
раціоналізацій, тому вона написана тут явно. Якщо перевірка червона, а рука тягнеться
дописати запис у baseline, послабити правило oxlint, знизити поріг покриття або додати
ключ приглушення в `knip.json` — це саме та поломка, від якої цей шар і будували.
`deadcode` навіть падає, якщо в `knip.json` з'явився будь-який ключ приглушення.

Виняток дозволений лише коли він: перелічений поштучно, датований, з причиною, яку
перевірено проти джерела, і сам себе скасовує, коли знахідка зникає.
